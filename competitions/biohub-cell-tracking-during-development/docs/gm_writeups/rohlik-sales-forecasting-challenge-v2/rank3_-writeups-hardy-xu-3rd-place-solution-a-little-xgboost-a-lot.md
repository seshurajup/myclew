# Optimizing (W)MAE
One thing that I experienced when using XGBoost, LGBM, etc. was that out of the box, setting the objective to MAE did not seem to produce better results than RMSE, even though the metric for this competition was a weighted MAE. Per a suggestion that I found in [this Stack Overflow post](https://datascience.stackexchange.com/questions/104743/optimizing-mae-degrades-mae-metrics), I decided to square-root transform the sales, since taking the mean squared error of the square root is kinda-but-not-really similar to taking the mean absolute error. This was what worked best for me. 

I tried using the weights in various ways, such as including them as features, using them to create sample weights for the training/validation sets, etc. but I was not able to find a productive use for them. I tracked both the unweighted and weighted MAE of my experiments, but I generally stuck to optimizing the unweighted MAE.

# Model Validation
Admittedly, I had a lot of trouble finding a model validation setup that I was satisfied with. I started out by constructing a holdout validation set using the most recent 2 weeks of the train set, and calculating the MAE on that set. This mostly worked, but there were a few instances where the validation set score and public leaderboard score went in wildly different directions. I eventually settled on using a 2nd holdout validation set from April 8th 2024 to April 22nd 2024. This specific time period was chosen because I noticed the test set period did not appear to have any holidays, and this was the latest period I could find that had no holidays. Generally speaking, if a change I made improved the MAE for both of these validation periods, it also improved my leaderboard score.

This approach worked well enough for feature engineering, but it utterly failed for hyperparameter tuning. There seemed to be a lot disagreement between the 2 holdout validation periods in terms of which hyperparameter values were good, and very often a set of hyperparameters that worked well in validation did not seem to translate to success on the leaderboard. I ended up doing the tried-and-true method of taking a bunch of garbage and mixing it together in the hopes of producing something good, or as data scientists like to call it, *ensembling*. I took 17 different 2-week holdout periods and had Optuna find optimal parameters for each of them.   I used each of these hyperparameters on the training pipeline in my notebook to generate a set of predictions and took an average of all of them.

One thing I found a little strange was that my holdout validation WMAE scores were always around 1.5-2.5 lower than my public leaderboard scores. I took care to ensure my validation was leak-free by not including any sales values from the validation period in any of my engineered features, and even tried different time periods for validation, but no matter what, the validation scores were always lower. Fortunately the gap between my validation and leaderboard scores stayed reasonably consistent, which gave me enough confidence to continue with my feature engineering and other experiments to lower my score.

# Putting it all together
The notebook contains the bulk of my solution. The main difference between that and my final solution is the previously mentioned ensembling of results from 17 different hyperparameters (decrease in WMAE of ~.55). I also did a bit of 2nd level stacking of predictions using a neural network, which gave a fairly negligible boost in score (~.04). I did a lot of testing with LightGBM as well, but the results were always a bit worse than XGBoost, and it didn't seem to help even in the stack.
