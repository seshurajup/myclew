## 1. Overview of the Approach

### 1.1 Models & Algorithms Used
My solution is based on the strong public baseline notebook shared by "ZaynYu". 
- **Core LLM**: I used `gpt-oss-120b` as-is without any additional fine-tuning or parameter training. The model is empowered with a Python code execution tool.
- **Voting Mechanism**: I ran 8 parallel solver instances and selected the final integer answer via a majority vote.
- **Time Control**: I kept the early-stopping rule from the public baseline, which dynamically allocates remaining time and stops early when a clear majority answer is reached among early solvers.

### 1.2 Validation Strategy & Data Preprocessing
To improve the prompt without overfitting to the Public Leaderboard (LB) or the reference.csv set, I established an offline validation process:
- **Data Collection**: I collected 1120 full-text LLM-generated answers.
- **Dataset Composition**: This dataset included 32 runs per problem across the 10 official reference problems (320 samples) and 16 runs per problem across 50 external hard math problems shared by participants (800 samples).
- **Analysis Workflow**: I extracted the full response text, problem context, and final answer correctness into a unified table (`llm_history.csv`). I then leveraged more capable LLMs to cross-check and categorize why `gpt-oss-120b` failed on incorrect instances.

### 1.3 Prompt Design
The main improvement was in the prompt design. Specifically:
1. **Use Python for Verification**: Based on patterns frequently observed in correct answers, I instructed the model to use Python for verification.
2. **Check the Constraints**: Since I observed an error pattern where the model overlooked constraints stated in the problem, I explicitly instructed it to identify and check the constraints while solving.
3. **Narrow the Search Space**: Since I also observed an error pattern where the model generated Python code with loops that were too large to finish within the time limit, I instructed it to narrow the search space appropriately.

## 2. Details of the Submission

### 2.1 How the original prompt was developed

#### 2.1.1 Error Analysis
I used an LLM that was more capable than gpt-oss-120b, because I expected it to analyze the responses 
more accurately.However, a stronger LLM can also suggest solution methods that are too advanced for gpt-oss-120b to 
follow.To avoid this, I also provided examples of correct responses generated by gpt-oss-120b.This helped me search for 
effective solution patterns that were still feasible for gpt-oss-120b to execute.

#### 2.1.2 Motivation Behind My Analysis Framework
To reduce the risk of overfitting, I used a separate set of 50 problems outside the official competition data while improving the solution.
The goal was to avoid relying too heavily on the public leaderboard or the reference problems.

When I started this experimental workflow, the public notebooks had already reached a very high score around 40/50. While it was impossible to know the exact individual accuracy for each of these 50 problems on the leaderboard, I envisioned the situation as follows:
[Hypothesis]
- 5 problems that are almost impossible to solve.
- 10 problems that fluctuate between correct and incorrect.
- 35 problems that are always answered correctly.

Under these circumstances, if I relied solely on the public leaderboard score to evaluate whether my model was improving, I felt I would end up overfitting to just those 10 unstable problems. Given that the score calculations are heavily influenced by the inherent randomness of LLM text generation and problem ordering, I wanted to avoid placing too much emphasis on this metric.

Since the final private evaluation would evaluate the models on completely unseen problems, my goal was to implement enhancements that targeted all branches of mathematics and various dimensions of difficulty. Using only 10 reference problems felt far too restrictive.

Furthermore, I reasoned that analyzing the full-text content of the responses would allow me to discover ways to make the outputs even more stable for problems the model was already answering correctly. I believed this qualitative evaluation would alleviate the risk of overfitting.

(I would like to express my utmost respect to the competitors who pushed the scores to such an incredibly high level around 40/50. Needless to say, the leaderboard score was a critically important metric for guiding the community's progress up to that point.)

### 2.2 What Was Tried and Didn't Work
During the development cycle, I explored several ideas that ultimately did not yield improvements and were discarded:
- **Intuition-based Prompting**: Instructing the model to reason or answer in Japanese.
- **Two-Step Self-Correction**: A prompt that forced a draft-then-finalize sequence.
- **Research-inspired Methods**: I experimented with prompts inspired by "Complexity-based Consistency".
- **Expanding the Voting Pool**: I tried scaling the parallel solver runs from 8 to 16. While some easy problems finished much faster, the answers that completed prematurely showed a slight degradation in precision, leading to an overall increase in errors.

    system_prompt = (
        'You are a world-class mathematical problem solver.'
        'The final answer is a non-negative integer in [0, 99999].'
        'Return only the verified final answer in \boxed{}.'
        'Before solving, you must:'
        '1) extract all explicit constraints from the problem,'
        '2) identify the mathematical structure (algebra / number theory / combinatorics / geometry / functional equation),'
        '3) choose a solution plan,'
        '4) use Python for verification when symbolic reasoning is insufficient.'
        'You must never guess.'
        'If a candidate answer is found, verify it against all constraints before finalizing.'
        'Prefer concise reasoning and avoid long unnecessary explanations.'
    )
    
    tool_prompt = (
        'Use Python as a verification and search tool.'
        'The environment is a stateful Jupyter notebook. '
        'You must use print() to output results.'
        'Always:'
        '- print intermediate key values needed for verification,'
        '- validate candidate answers against all stated constraints,'
        '- avoid brute force unless the search space is explicitly bounded or pruned,'
        '- estimate complexity before large loops,'
        '- keep code minimal and robust.'
    )
    
    preference_prompt = ( 
        'Solve the problem with the following protocol:'
        'Step 1: Extract constraints and target form.'
        'Step 2: Derive reductions before coding (parity, modular constraints, bounds, symmetry, invariants, monotonicity, geometric relations, etc.).'
        'Step 3: Use Python only for:'
        '- checking candidate formulas,'
        '- bounded search after pruning,'
        '- validating edge cases,'
        '- confirming the final answer.'
        'Step 4: If using search, explain the pruning rule first.'
        'Step 5: Before final output, verify:'
        '- integer,'
        '- in [0, 99999],'
        '- all constraints satisfied.'
        'Step 6: Return only the final verified answer in \boxed{}.'
        'Keep reasoning compact. Never guess. If verification fails, discard the candidate and continue.'
    )
