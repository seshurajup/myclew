### Text cipher

The trace builds the mapping that decrypts the letters by looping through the examples, then applies it to the query. The model then guesses the phrase and the sentence template using the 77-word vocabulary and the 4 sentence templates.

What follows is an error-correction loop. The trace iterates each word in the sentence template, and for each word, it finds the corresponding word type (subject, verb, object, location, preposition, adjective) and loops through all words of that word type. I restrict candidates to those within one letter of the decoded length, then score: 1 point for a matching length, 10 per known letter, and 1 per still-missing letter, with the top-scoring word declared as the "true" word.

Overall, the error-correction scheme improved text cipher from $\sim 98.5\%$ to $\sim 99.5\%$, given the same number of training examples. The remaining failure modes were guessing the wrong sentence template or performing the error correction correctly only to substitute the guessed word in the final phrase.

### Equation transform / numeric

#### Data generation process

Each problem fixes one **domain**, *normal* or *reversed*, shared by every example, and assigns each of its (typically three) distinct operators a single base arithmetic family — subtraction, addition, multiplication, or concatenation. The base relation is perturbed within its family (+/-1 for addition and multiplication; absolute value and negation for subtraction; modulo, written `max%min`, lives inside the subtraction family) and the chosen domain is applied. The 11 arithmetic rules each appear in a *normal* and a *reversed* form (22), and the 2 concatenation rules are domain-independent, for a total of 24 rules. Across the 732 problems, the *normal* domain accounts for 286 (39.1%) and the *reversed* domain for the other 446 (60.9%).

| Subtraction | Addition | Multiplication | Concatenation |
|---|---|---|---|
| `a-b` | `a+b` | `a*b` | `cat(a,b)` -> `abcd` |
| `b-a` | `a+b+1` | `a*b+1` | `cat(b,a)` -> `cdab` |
| `\|a-b\|` | `a+b-1` | `a*b-1` | |
| `-\|a-b\|` | | | |
| `max%min` | | | |

Two other notes:
- For subtraction, a negative result is marked with the operator character before the digits (`opN`) or after (`Nop`), fixed per problem. The placement gates the signed rule: a prefix marker excludes `b-a` and a suffix marker excludes `a-b`, pruning the wrong-direction subtraction.
- **Concatenation does not carry the domain.** It is its own family with two orderings, `cat(a,b)` → `abcd` and `cat(b,a)` → `cdab`, chosen independently per operator. A concatenation operator looks the same whether the problem is normal or reversed, so it never reveals the domain and takes no part in the normal-vs-reversed decision.

#### Procedure

Each distinct operator can be one of 24 rules to start. We iterate through the examples in the problem. The examples eliminate rules that fail to reproduce the output *exactly* as a string — leading zeros and sign placement included. After this per-example pass, an operator that appears in the examples is typically down to 1-3 candidates.

Attention then turns to the query operator. If it has not been seen, it starts with all 24 rules. We then narrow the candidate rules for the query operator based on five filtering steps:
1. **Normal vs. reversed from rules.** If there is at least one example operator with only *normal* or *reversed* rules remaining, this pins the query operator's domain. Concatenation operators abstain.
2. **Normal vs. reversed from zeros in the query.** A leading zero in the query's own operands (e.g. `08`) pins the reversed domain, and a trailing zero (e.g. `50`) pins the normal domain.
3. **Base arithmetic family based on the other symbols.** No two operators share the same base relation (subtraction, addition, multiplication). Let the other operators claim their family; assign the query operator to the bucket that is left. If multiple buckets remain, the priority is subtraction, addition, and multiplication. Note that I expected at most three distinct operation symbols in a problem.
4. **`a-b` vs `b-a` for subtraction.** The position of the negative-sign marker encodes `a-b` versus `b-a`, pruning the wrong-direction subtraction rule.
5. **Base family based on query glyph.** If the query glyph is a literal `+`, `-`, or `*`, survivors are restricted to that family. This rule comes from the observation that `+`, `-`, or `*` are most frequent and normally represent addition, subtraction, or multiplication, respectively.

Whatever survives is committed in a fixed priority order — by domain (normal before reversed, concatenation last), and within a domain by family (subtraction, then addition, then multiplication, each taking the canonical rule before its +/-1 or sign variants) — so the procedure always emits a single best guess rather than abstaining.

### Bit manipulation

My solution builds off directly from [huikang](https://www.kaggle.com/huikang)'s [bit manipulation solution](https://www.kaggle.com/competitions/nvidia-nemotron-model-reasoning-challenge/discussion/690307), which solves 85% of problems. With reasonable hypotheses about the data generation process, this solution solves 99% of problems.

#### Hypothesized generator

Denote `P` as an atom. Atoms can be one of 21 operations on the input (3 atom types × 7 shift amounts): rotate-left `ROTk` (cyclic, bits wrap), shift-left `SHLk`, and shift-right `SHRk` (both zero-fill), where **$k \in 1..7$** ($k \in 1..7$ vs. $k \in 0..7$ is important later). Binary operations between atoms include `AND`, `OR`, `XOR` (e.g. `P1 op P2`) and the negated-second-operand variants `ANDNOT`, `ORNOT`, `XORNOT` (e.g. `P1 op ¬P2`). Denote `OP` as any one of these six binary operations, and let `a` denote the left shift amount, `b` the left rotation amount, and `c` the right shift amount. Every rule belongs to the following grammar:

| Family | Order | Form | Share |
|---|---|---|---|
| no-op  | 1 | `P` | 9.1% |
| one-op | 2 | `P1 OP P2` | 51.6% |
| 2-op (Shape A/B) | 3 | `(SHRc OR ¬ROTb) XOR SHLa` or `(SHLa XOR ¬ROTb) OR SHRc` | 18.7% |
| Majority    | 3 | `Maj(SHLa, SHRc, ROTb)` | 12.4% |
| Choice     | 3 | `Ch(SHLa, SHRc, ROTb) = (SHLa AND SHRc) OR (¬SHLa AND ROTb)` | 4.7% |
| 2-op (Shape C) | 3 | `((SHLa XOR ¬ROTb) OR SHRc) AND ¬(SHLa AND ROTb AND SHRc)` | 3.5% |

In the table above, the **order** denotes the number of distinct atoms used (an *n*-op rule applies *n* binary ops to *n+1* atoms, hence order *n+1*). A rule's **signature** is its per-bit operator pattern:

| bit | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| `SHLa` | IN3 | IN4 | IN5 | IN6 | IN7 | | | |
| `ROTb` | IN1 | IN2 | IN3 | IN4 | IN5 | IN6 | IN7 | IN0 |
| `SHRc` | | | IN0 | IN1 | IN2 | IN3 | IN4 | IN5 |
| **region** | L | L | M | M | M | R | R | R |

Each cell shows the input bit `INx` that atom reads (`SHLa[i] = IN(a+i)`, `ROTb[i] = IN((b+i) mod 8)`, `SHRc[i] = IN(i-c)`). An atom is **live** at a bit when it reads a real input bit, and **dead** (zero-filled, shown blank) when its shift has run off the end: `SHLa` is dead past bit `7−a`, `SHRc` before bit `c`, while `ROTb` is always live since it wraps. The output thus breaks into contiguous **regions.** For every family, there are at most 3 regions in the signatures. In general, the number of regions equals the rule's order (here both 3).

For example, `Maj(SHL3, SHR2, ROT1)` has three regions resolving as:
- **Left** (bits 0–1): `SHR2` is dead (zero-filled), so `Maj(SHL3, 0, ROT1) = AND(SHL3, ROT1)` — a 2nd-order AND, written `AND13`.
- **Middle** (bits 2–4): all three atoms are live, so the full 3-input `Maj(SHL3, SHR2, ROT1)`, written `Majority316` (the `6` is from `8-c=8-2=6` since a right shift by `c` equals a left rotation by `8-c` over the non-zero portion).
- **Right** (bits 5–7): `SHL3` is dead, so `Maj(0, SHR2, ROT1) = AND(SHR2, ROT1)` — again a 2nd-order AND, written `AND61`.

It's possible that the number of regions for a rule is less than its order. For example, consider `Maj(SHLa, SHRc, ROTb)` with `a = b`. For bits `0` through `7-a`, `SHLa` equals `ROTa`, and since `Maj(ROTa, SHRc, ROTa) = ROTa`, those bits are the input rotated left by `a` (which I denote as `Ia`). Bits `8-a` to `7` are `Maj(0, SHRc, ROTb)`, which equals the `AND` between the input shifted right by `c` and the input rotated left by `b` (which I denote as `ANDb{8-c}`, again since a right shift by `c` equals a left rotation by `8-c` over the non-zero portion). Hence, this `Maj` rule leaves a two-region signature.

Importantly, under the data-generation hypothesis, `a`, `b`, and `c` range from 1 to 7. Because every shift is at least 1, `SHRc` is dead at bit 0 and `SHLa` is dead at bit 7, so both left and right regions have at most two live atoms (the always-live `ROTb` plus either shift). Therefore, for every rule in the grammar, the left and right regions (for no-op, these overlap on all 8 bits) are at most 2nd-order functions of the input:
- **0th-order** (`LOW`, `HIGH`): the output bit is a constant 0 or 1, reading no input bit.
- **1st-order** (`Identity`, `NOT`): the output bit is a single (rotated) input bit, as-is or complemented.
- **2nd-order** (`AND`, `OR`, `XOR`, `ANDNOT`, `ORNOT`, `XORNOT`): the output bit is a boolean function of two (rotated) input bits.

This fact justifies why we only need to consider these 10 functions for the corner regions (the left region that includes bit 0 or the right region that includes bit 7). Further, the corner regions can narrow down the operator pattern for the middle region and determine how long the regions should be: this means we can enumerate left/right region pairs, filter for pairs that fit the signature, and use the left/right pairings to determine the signature. "Final summary E" of [this MD file](https://github.com/livctr/nvidia-nemotron/blob/main/nemotron/data/docs/bit_manipulation_bit_formulas.md) includes a comprehensive list of signatures. The middle region is one of three forms — `LOW`, `NOT`, or an "unknown" function. Only the unknown case needs a brute-force check.

After summarizing the runs, we determine which candidate signatures to enumerate. As was conjectured by the data-generation hypothesis, every signature in the table falls into one of four cases by region count (the specific signatures are located in [bit_manipulation_bit_formulas.md](https://github.com/livctr/nvidia-nemotron/blob/main/nemotron/data/docs/bit_manipulation_bit_formulas.md)):
- **One region (no-op):** the whole output is one operator: `Ib` (rotation), `HIGH`, or `ANDab` (a `Maj` collapsed to one `Ix AND Iy`).
- **Two region (one-op, or merged-twin multi-op):** Left + Right, no live middle — a one-op rule, or a multi-op whose two corners are the same op on a shared digit (e.g. `ANDab`/`ANDbc`).
- **Three region, middle `LOW` or middle `NOT`:** Left + Right + a constant/negation filler. This case occurs when the dead part of SHL and SHR overlap.
- **Three region, UNKNOWN middle:** the middle is 2nd-order or higher (`Majority`, `Choice`, a 2-op (Shape A/B), or `XOR`-shift). This case occurs when SHL and SHR have no overlapping dead part (e.g. when both `a` and `c` are small).

If a family pair is "long", we display every shift-tagged operator in the left family that matches the shift (here "7" from NOT745; every other region enumeration has no such shift requirement), each taking a line. When the middle is *live* (not this example), we predict the middle-region form from the family pair and verify bit-by-bit. For example, `AND`/`AND` indicates `Majority`, `ANDNOT`/`Identity` indicates `Choice`, `Identity`/`Identity` indicates `XOR`.

The block below shows ID `00890aff` with rule `Maj(SHL2, SHR1, ROT6)`: the `AND`/`AND` corners `AND26`/`AND67` (shared `b = 6`) predict the middle `Majority267`, verified against every example.

Because all middle bits match for `Majority267`, that becomes our middle. `Choice` is handled similarly, but because `c` never shows at the corners, the trace sweeps `c = 1..7` (e.g. ID `000b53cf`). Up to now, every family except for 2-op (Shape C) is handled.

Finally, we do two fallbacks, which are run when no candidate has a length error below 4:
1. *Over-run.* We may have a spurious match longer than the true match in a op family. We search the runs within the families until the first hit with length error 0 (e.g. ID `649bebaf`).
2. *Shape C.* If no shorter corner fits, take the longest `XORNOT`/`ORNOT` pair and evaluate Shape C, `((SHLa XOR ¬ROTb) OR SHRc) AND ¬(SHLa AND ROTb AND SHRc)` (e.g. ID `05b5ffe1`).

The last 1% of rows have more than one signature fitting the 7-10 examples, making prediction ambiguous. We order the testing of signatures such that the first candidate to achieve the smallest length error has lower order (e.g. ID `82d937aa`).

Overall, this solution:
1. Keeps in mind the 7680-token budget: employs hex-binary, avoids double computation for commutative binary ops, enumerates two-region and three-region with middle `LOW` or middle `NOT` only when necessary, and minimizes per-bit brute-force verification by stopping at the first full match.
2. Reduces spurious matches by considering nonzero-shift operators only and matching based on signatures.
3. Uses shift logic to determine the middle bits and true region lengths.

### Equation transform / symbol

I largely left this category alone. For $n$ distinct digits, a brute-force solver would have to enumerate $n!$ symbol-to-digit mappings. Assuming each `ab [op] cd = x` takes at least 7 tokens, that gives a testing budget of 1100 combinations, which means we can only enumerate over 6 distinct symbols at most (6! = 720, 7! = 5040, only two problems of 823 have <=6 distinct symbols). Other top teams used a "signature-based" prediction idea similar to the one I used for bit manipulation: the form of `ab [op] cd = x` tells you which symbol-digit mappings to enumerate, reducing the search space.

My solution follows the idea by [huikang](https://www.kaggle.com/huikang) in the [Open Progress Prize Publication](https://www.kaggle.com/competitions/nvidia-nemotron-model-reasoning-challenge/discussion/689915). It handles concatenation and reversed concatenation. Touch-ups include:
- Guessing the first symbol seen when it is clear the query operator is neither concatenation nor reversed concatenation.
- Refining the trace to look more similar to my solution for equation transform / numeric.
- Using the non-ASCII delimiter `│` and the Nemotron tokenizer to make parsing easier to understand for the Nemotron model. This is the reason behind the strange spacing and newlines in the below trace. I found that this helped roughly 5-10 examples of the 823 total examples.
- To deal with `}` symbols, I emit in the format `The final answer is: <answer>` rather than `\boxed{<answer>}`. This format is replicated to the other categories for consistency.

## Modeling and workflow

### Workflow

1. Make edits under `nemotron/data/main/` in [my repo](https://github.com/livctr/nvidia-nemotron) and create/edit a configuration file under `configs/`.
2. Generate data via `bash generate_traces.sh --config configs/final.yaml`.
3. Train the model and auto-submit to my Kaggle notebook for validation: `bash train_sft.sh --config configs/final.yaml --backend [mbridge|tinker] --experiment my_experiment`.
4. Analyze results with `bash analyze_adapter.sh --pull-kaggle`.

To figure out my hypotheses for the data generation process, I would ask Claude questions and have it write scripts under `scripts/discovery`. Claude wrote the orchestration in my code and wrote 95% of the data generation code, with some formatting changes made by me.

To save training tokens during the experimental process, I noticed that I could focus on one domain at a time. For example, I could train and validate just on text cipher. This was very useful before coming to bit manipulation since the other categories required far fewer tokens to train.

### Tinker vs Megatron-Bridge training infrastructure

My early experiments ran on Tinker, but switching to Megatron-Bridge turned out to matter a lot: in one run, changing nothing but the backend raised bit manipulation accuracy from 0.81 to 0.89 (against a synthetic-trace ceiling of 0.91 for the category at the time). The reason is that a Tinker LoRA requires a lossy SVD to be converted into the PEFT format, whereas a Megatron-Bridge LoRA maps to PEFT exactly.

Late in the competition, I discovered a bug in my [code](https://github.com/livctr/nvidia-nemotron/blob/main/nemotron/submit/mbridge_peft_extract.py) that converts the Megatron-Core distributed checkpoint into a HF PEFT adapter. I caught it late because my internal validation scores stayed high despite it, and fixing it made little difference: public LB went 0.884 -> 0.880 and private LB stayed 0.908. Megatron stores a fused QKV projection for the attention layers, and my extractor split the `B` LoRA matrix into separate q/k/v with a plain contiguous slice, whereas Megatron interleaves Q/K/V per query group. The bug thus mixed up Q, K, and V rows. I find it strange that my internal validation was still so high even with this bug. I can only hypothesize that most of the adaptation lives in other layers, especially the MoE layers.

Notes:
- Validation results were generally quite robust to the learning rate (between 1e-4 and 3e-4).
- `moe_grouped_gemm: false` attaches a per-expert LoRA.
- `expert_model_parallel_size: 4` with 4 GPUs shards the base model's 128 experts across them (32 per GPU), cutting per-GPU memory enough to fit the 8192-token sequence length. I did not realize at the time that this layout tiles the LoRA weights across the sharded experts: only 32 distinct A/B matrices are learned for the 128 experts, cutting LoRA capacity ~4x (≈880M → ≈220M free parameters). I don't think this had a large impact on the final results — the synthetic vs. LoRA-emitted traces differ by only $0.3\%$ accuracy.
- There are large diminishing returns after around 80M tokens. I believe it would have been possible to place second in this competition with a LoRA trained on 80M tokens. Designing accurate and learnable traces was more important (and also more human-intensive).
- Training `output_layer` is extremely important, especially if you want to include tokens in the long-tailed end of the vocabulary (e.g. the non-ASCII `│` separator).

## Conclusion

My key ingredient in this competition is synthetic data generation. As [huikang](https://www.kaggle.com/huikang) mentions [here](https://www.kaggle.com/competitions/nvidia-nemotron-model-reasoning-challenge/discussion/689915), it helps to think of the adapter as a computer. This computer manages:
- **Storage**: facts the weights can memorize during training (e.g. the bit manipulation signatures, text cipher words).
- **Compute**: each reasoning step should use inputs that are already explicitly in the trace. The smaller the positional distance between an input and the step that consumes it, the better.
